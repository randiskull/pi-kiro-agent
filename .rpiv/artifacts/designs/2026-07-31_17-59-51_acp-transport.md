# Design: pi-kiro v2 ACP Transport

## Summary

Replace the TUI-scraping chat transport (`stream-adapter.ts`) with a persistent
`kiro-cli acp` child per cwd that communicates over NDJSON JSON-RPC 2.0 (ACP).
The new transport (`acp-transport.ts`) runs behind `PI_KIRO_TRANSPORT=acp` with
the chat transport untouched as the default. Tool mounting moves from per-turn
agent profile files to the protocol-native `session/new.mcpServers` array
(Option B, probe-gated); sentinel, exit-salvage, and snapshot-diff code are
deleted per the §7 DoD.

## Requirements

- Replace stdout-parsing + sentinel + exit-salvage with ACP protocol events
- Persistent child per cwd; 10-minute idle timeout (§3.1)
- NDJSON JSON-RPC 2.0 transport (probes confirmed; NOT LSP framing)
- `session/new` with bridge + gsd-workflow servers inlined as `mcpServers` array (Option B)
- Per-session bridge: one `getBridge()` call per ACP session, closed at session end
- `session/update` streaming: `agent_message_chunk` → thinking/text events
- `tool_call` session/update events → `ToolCall` content blocks (first-class, no synthesis)
- Credits from `_kiro.dev/metadata.meteringUsage[].value` (sum all on final notification)
- Divergence detection: prefix hash mismatch → `session/new` on same child (full context resend)
- Gate behind `PI_KIRO_TRANSPORT=acp`; default (chat) transport unchanged
- Delete sentinel (`FINAL_OPEN`/`FINAL_CLOSE`), exit-salvage heuristic, snapshot-diff code
- `writeAgentProfile()` unchanged (chat transport still uses it)
- `discoverWorkflowMcpServers()` unchanged (only injection point moves)
- Parity test suite covering all stream-adapter.test.ts scenario classes

## Current State Analysis

- `index.ts:73` — `streamSimple: makeStreamViaKiro(deps)` wired at registration; `PI_KIRO_TRANSPORT=acp` gate added (index.ts:103-108)
- `kiro-bridge.ts:37` — `writeAgentProfile(handle?, extraMcpServers?)` untouched; chat transport continues to use it
- `workflow-mcp.ts:59` — `discoverWorkflowMcpServers(cwd)` returns `Record<string, KiroStdioMcpServer> | undefined`; reused as-is
- `probes/p3-gate-option-b.json` — Option B probe gate PASSED: both HTTP (pi) and stdio (gsdworkflow) mount and resolve under bare names via `session/new.mcpServers`

### Protocol findings (kiro-cli 2.16.0, probes/probe-findings.md)

| Finding | Impact |
|---|---|
| NDJSON (NOT LSP framing) | readline-based client |
| `protocolVersion: 1` (integer) | pin at initialize |
| `session/prompt.prompt` (NOT `content`) | field name |
| `session/update` (NOT `session/notification`) | method name |
| turn completion = prompt response (`stopReason: "end_turn"`) | no TurnEnd event |
| credits in `_kiro.dev/metadata.meteringUsage[].value` | sum all entries |
| `initialized` notification → -32601 | skip it |
| `session/cancel` → -32601 | abort = SIGTERM |
| `session/new.mcpServers` is ARRAY | `[{type:"http",...}, {command,...,env:[]}]` |
| sessions are per-process | keep child alive across turns |
| `_kiro.dev/commands/available` must arrive before `session/prompt` | startup gate |
| stdio env is `Array<{name,value}>` on wire (not object) | format conversion needed |

### Three bugs found and fixed during implementation

1. **`commands/available` race** (`startSession`): listener registered AFTER `session/new` response → notification arrived before listener registered → `MCP_STARTUP_TIMEOUT_MS` timeout. Fix: register listener before sending `session/new`.

2. **Abort mid-spawn** (`spawnAcpChild`): `onAbort` handler in `makeStreamViaAcp` called `childRegistry.get(cwd)` but child not added to registry until after `initialize` response → abort during handshake found no entry → hung forever. Fix: add entry to registry BEFORE the `initialize` handshake.

3. **Spurious divergence on first turn** (`makeStreamViaAcp`): `planAcpTurn` returned `{mode:"fresh"}` (no recorded sessions) but `acpEntry.acpSessionId` was already set by `startSession` → `!useResume && acpEntry.acpSessionId` condition fired → spurious session/new reset. Fix: move session lifecycle OUT of `getOrCreateChild`; session creation/reuse/divergence handled entirely in the `makeStreamViaAcp` IIFE after planning.

## Scope

### Building

- `acp-session.ts` — ACP session state (hash-based divergence detection, `planAcpTurn`, `recordAcpSession`, `advanceAcpSession`, `dropAcpSession`)
- `acp-transport.ts` — `makeStreamViaAcp` factory (persistent child, NDJSON client, session lifecycle, streaming)
- `acp-transport.test.ts` — full parity test suite (18 tests)
- `index.ts` — `PI_KIRO_TRANSPORT=acp` gate (already wired)

### Not Building

- `session/load` resume (complex history replay; see Decisions for the legitimate future use case)
- v3 stable agent profile (kiro v3 has no working headless mode)
- Auth-callback handler (probe confirmed `authMethods: []` for IdC seats)
- Deletion of `session-manager.ts` or `stream-adapter.ts` (kept; chat transport default)
- Any changes to `writeAgentProfile()`, `discoverWorkflowMcpServers()`, `kiro-bridge.ts`

## Decisions

### Pattern: Follow makeStreamViaKiro factory

Same `StreamDeps`-style injection (`AcpDeps`), async IIFE inside stream, same event push sequence (start → thinking_start/delta/end → text_start/delta/end → done/error). Tests mirror `stream-adapter.test.ts` with NDJSON protocol fakes.

Evidence: `stream-adapter.ts:216-407`; developer confirmed Q1.

### Transport: NDJSON readline, JSON-RPC 2.0 over stdio

`spawn("kiro-cli", ["acp", "--trust-all-tools", "--agent-engine", "v2"])` with `createInterface({ input: child.stdout })`. Each message is `JSON.stringify(msg) + "\n"`. Confirmed by P0 raw sniff.

### Tool mounting: Option B — inline `session/new.mcpServers` (probe-gated ✓)

Bridge and gsd-workflow servers passed in `session/new.mcpServers` array. No agent profile file for ACP turns. `writeAgentProfile()` untouched (chat transport still uses it). Probe gate: `probes/p3-gate-option-b.json` — both server types mounted and resolved.

Rationale (developer-stated): Option A is incompatible with the persistent-child model — a per-turn loopback bridge (fresh port+token per turn) would be stale in a profile read once at spawn. Per-session mounting is the correct lifetime under ACP.

Wire format for stdio: `{ name, command, args, env: [{name, value}] }` (env is array, not object — probe confirmed). `buildMcpServersConfig()` converts `KiroStdioMcpServer.env` object → array.

§3.3/§6 amendment: the "unchanged by design" constraint governs the tool SURFACE and discovery code (unchanged); the delivery vehicle moves to the protocol-native field.

### Bridge lifetime: one bridge per ACP session

`getBridge()` called once at session creation, stored on `AcpChild.bridge`, closed at session end (divergence reset / idle-timeout / child crash). This matches the per-session tool list stability requirement.

### Divergence: `session/new` on prefix hash mismatch

On mismatch: `dropAcpSession`, reset `acpSessionId`, close old bridge, create new bridge, call `startSession` on same child. Full context resend.

**Why not `session/load`**: divergence means pi's context is authoritative AND has changed (compacted, edited, truncated). `session/load` replays the stale kiro history that divergence just invalidated — it would recreate the exact stale-context bug the v1 reset rule exists to prevent. The v1 session-manager's unconditional reset-on-divergence rule is correct here. Developer confirmed Q4.

**`session/load` legitimate use (future optimization — not in v1)**: child-restart recovery when the prefix is UNCHANGED — the supervisor restarted the kiro-cli child after a crash or idle-reap, but pi's conversation did not change. In that case, replaying history avoids a full re-send. However, v1 ships with the single proven-correct code path: everything abnormal (divergence OR child restart) → `session/new` + full re-send. The load-replay optimization carries its own risk (replay-consumption state machine complexity) and should only be pursued if field usage shows child restarts are frequent enough to matter.

### Idle timeout: 10 minutes (§3.1)

`IDLE_TIMEOUT_MS = 10 * 60 * 1000`. Timer reset after each successful turn. Fires `killChild("idle timeout")`. Next turn respawns.

### ACP protocol version: pinned at `protocolVersion: 1`

Guards against kiro-cli drift. kiro-cli went 2.13→2.15→2.16 in ~3 weeks (§5 row 1 confirmed).

### Session lifecycle architecture: session creation outside `getOrCreateChild`

`getOrCreateChild` only spawns + initializes the child process (`initialize` handshake). Session creation (`session/new` + `startSession`) happens in the `makeStreamViaAcp` IIFE after `planAcpTurn` determines the turn mode. This avoids spurious divergence resets on first turns.

### acp-transport.ts — NEW

Key exports: `makeStreamViaAcp(deps: AcpDeps)`, `_resetAcpChildren()`.

Session lifecycle flow:
1. `getOrCreateChild(deps, cwd, signal)` — spawn + initialize only (no session)
2. `planAcpTurn(cwd, acpEntry.acpSessionId, messages)` — plan turn
3. If no `acpSessionId` → `getBridge()` + `startSession()` (first turn)
4. If `!useResume` → divergence reset + new `startSession()`
5. If `useResume` → reuse existing session

`startSession` registers `_kiro.dev/commands/available` listener BEFORE sending `session/new` (race fix).

`spawnAcpChild` adds entry to `childRegistry` BEFORE `initialize` handshake (abort-mid-spawn fix).

See full implementation at `acp-transport.ts`.

## Verification Notes

- **kiro-cli 2.16.0** — third version drift during this project (2.13→2.15→2.16 in ~3 weeks). Pin `protocolVersion: 1` at initialize; CI must re-run probe fixtures when CLI bumps.
- **Session-per-process** (P5): sessions die with the child. Transport must handle unexpected child exits as full-session loss → re-spawn on next turn.
- **`_kiro.dev/commands/available` gate** (P2/P3): must arrive before sending `session/prompt`. Register listener BEFORE sending `session/new` to avoid the race.
- **Abort mid-spawn**: add entry to `childRegistry` BEFORE `initialize` handshake; abort handler can then find and kill mid-handshake.
- **`session/cancel` → -32601**: abort = SIGTERM only (no protocol-level cancel).
- **`initialized` notification → -32601**: skip silently.
- **stdio env on wire**: `Array<{name: string, value: string}>` not `Record<string, string>`.
- **DoD items** (§7): sentinel (`FINAL_OPEN`/`FINAL_CLOSE`), exit-salvage heuristic (commit 32df5c3), `synthesizeToolCallBlocks`/`parseKiroToolUses`, snapshot-diff (`snapshotSessions`/`recordFreshSession`/`makeListSessions`) — all absent from `acp-transport.ts` (verified by DoD test suite).
- **Field gate** (§4.4): one full GSD milestone slice on `PI_KIRO_TRANSPORT=acp` with zero salvages and zero synthesized tool calls.
- **Parity suite** (§4.3): `npm test` — 91 passed, 1 skipped (live integration).

## Performance Considerations

- Persistent child eliminates per-turn spawn overhead (~150-300ms cold start).
- Session reuse (delta prompt) eliminates full context resend on subsequent turns in the same conversation.
- Idle timeout (10 min) bounds resource usage for long-idle sessions.
- `discoverWorkflowMcpServers` runs once per turn (file system walk) — same as chat transport.

## Migration Notes

- Chat transport (`stream-adapter.ts`) remains the default. No migration required for existing users.
- To opt in: set `PI_KIRO_TRANSPORT=acp` in environment before launching pi.
- `session-manager.ts` remains for the chat transport; not touched by this design.
- `writeAgentProfile()` / agent profile files continue to exist for the chat transport.

## Developer Context

**Q1 (Direction)**: Follow `makeStreamViaKiro` factory pattern → Follow makeStreamViaKiro pattern

**Q2 (Idle timeout)**: §3.1 specifies 10 min → 10 min (as per §3.1)

**Q3 (Tool mounting)**: Option B — inline `session/new.mcpServers` with four conditions:
1. PROBE-GATED: `probes/p3-gate-option-b.json` confirms both HTTP + stdio servers mount and resolve ✓
2. REUSE, don't rewrite: `discoverWorkflowMcpServers()` and bridge construction unchanged
3. Rationale: Option A incompatible with persistent-child model (per-turn bridge would be stale in profile)
4. Spec §3.3/§6 amendment: "unchanged by design" governs the SURFACE, not the delivery vehicle

**Q4 (Divergence)**: `session/new` on prefix hash mismatch → session/new on divergence (Recommended)

Full rationale (developer note): not just simpler — `session/load` would replay the very history that divergence has invalidated (pi compacted/edited; pi's context is now authoritative), recreating the stale-context bug the v1 reset rule exists to prevent. `session/load` DOES have a legitimate future use: child-restart recovery with an UNCHANGED prefix (supervisor restarted kiro-cli after crash/idle-reap, pi's conversation unchanged). That would avoid a full re-send. But v1 ships with the single safe code path — everything abnormal → fresh session — and parks the load-replay optimization for after field evidence shows child restarts are frequent. Optimization risk: replay-consumption state machine complexity.

**Design confirm**: Proceed (Recommended) → decomposed into 4 slices
