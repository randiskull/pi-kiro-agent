## Findings
- [G3] "## Verification plan": no step is a negative control. None names a check run on the unchanged tree, says it fails there and gives the mechanism. The manual reproduction runs only "after the change", and the unit and live tests are described only as passing. Fix: add a `- **Negative control**` bullet. For example, run the criterion 3 child-process test (or live case 2) on the current tree and state that it does not exit within the bound, because the referenced `TCPServerWrap` from `serveBridgeHttp()` holds the event loop. Do the same for the startup-gate test (the child is unref'd as soon as `session/new` settles). Then state that both pass after the change. This is also the step-2 check `docs/releasing.md` requires before a `### Fixed` bullet may cite the test.
- [D2] "**Bridged calls arrive only mid-turn.**": the argument covers a tool call that is still in flight. It does not cover the HTTP keep-alive sockets that kiro's MCP client leaves open after a bridged call is answered. Those accepted sockets are still referenced, so a one-shot host can stay alive until the server's keep-alive timeout closes them, and nothing in the spec bounds or tests that. Fix: state the bound (Node's `server.keepAliveTimeout`, or close idle connections once the turn ends), and make live case 2 assert that exit follows `bridge.result` within that bound.
- [D2] "A one-shot host (`pi -p`, GSD headless, any print-mode or scripted run) that": the Goal names GSD headless and scripted hosts, but "Why this is safe" argues only `pi -p`, chat and interactive pi. It does not argue GSD headless or RPC-mode hosts, or in-process subagent sessions sharing the module's child registry. Fix: add the argument for each of those contexts, or narrow the Goal.
- [D3] "`docs/design/acp-transport.md` §5e.3,": the keepalive design this change extends is in `docs/design/acp-transport.md` section 5 (Risks & open questions, the one-shot exit row), with the child lifetime model in section 3.1. Neither is cited, and the spec does not say whether that section 5 row will be updated to name the bridge listener. Fix: cite section 5 and section 3.1, and say whether the section 5 row is amended.
- [D4] "spawn the real `pi -p` with ACP and the bridge enabled.": the live test says what to strip but not what it needs: a `pi` binary, an authenticated kiro-cli seat, and an agent home that has at least one bridged-tool extension installed. Case 1 also does not assert a `bridge.serve` event. In a clean home `serveBridgeHttp()` returns `undefined`, so case 1 passes with no listener at all, which is the same trap the spec identifies in 8ec09e2. Fix: list the environment requirements, and have case 1 also assert a `bridge.serve` trace event.
- [D5] "- Target release: pi-kiro-agent 0.4.1 (patch)": the bump is not justified against the table in `docs/releasing.md`. Fix: say it is a patch because it is a bug fix that changes no `PI_KIRO_*` variable, command, model id or floor.
- [D5] "CHANGELOG `## 0.4.1` → `### Fixed` describes the symptom, the cause and the": `docs/releasing.md` puts `### Fixed` bullets under `## Unreleased` and cuts a release by renaming that heading. `## Unreleased` already holds a `### Changed` entry and two #58 `### Fixed` entries, which would ship in 0.4.1. The spec does not say so. Fix: add the bullet under `## Unreleased` → `### Fixed`, and either say the cut to 0.4.1 includes the existing Unreleased entries (and that the patch bump still fits them) or leave the cut to a separate release PR.
- [D5] "The bullet cites the criterion 3 test by file and test name, as": criterion 3 covers two fixes, the unref and the startup-gate keepalive, which are separate tests in the Verification plan. `docs/releasing.md` allows one claim per bullet, so one bullet citing one test leaves one fix ungated. Fix: write two `### Fixed` bullets, each citing its own test, or one bullet per test.
