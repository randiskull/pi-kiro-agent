## Findings
- [D2] "Each accepted connection is its own referenced socket for its lifetime, so an in-flight tool call keeps the process up until it is answered.": by the same property, the keep-alive connection kiro's MCP client holds open after a bridged call stays a referenced socket after the turn ends, until the server's keepAliveTimeout closes it. That post-turn context is neither argued nor bounded by a test. Fix: say how long an idle accepted socket can hold the host (Node's default keepAliveTimeout, or close idle connections once the turn settles), and give the bridged live case an exit bound that would catch a socket that never closes.
- [D2] "Today the referenced bridge listener holds the loop open through that wait.": the Observed failure row `PI_KIRO_BRIDGE=off` exits 0 with no listener at all, so the gate wait finishes there without the hold the spec says is needed. The spec does not say what keeps the loop alive in that run, or that the gate is empty or synchronous there, so the startup-gate argument is incomplete. Fix: state which servers the gate waits on with the bridge off, and why that run survives the gate.
- [D3] "The keepalive invariant (ref the child while `pending > 0`, and through the startup gate)": `docs/design/acp-transport.md` §5 (the one-shot-exit row of the risks table) documents that `setChildKeepalive` unreferences the child "whenever `pending` is empty". The spec changes that invariant but does not cite that section or plan to update it. Fix: cite §5 and add the design-doc row update to In scope and Approach.
- [D4] "spawn the real `pi -p` with ACP and the bridge enabled.": the first live case neither requires an agent home with a bridged extension installed (for example `@juicesharp/rpiv-todo`) nor asserts a `bridge.serve` trace event. With no bridged tools, `serveBridgeHttp()` returns `undefined`, so the case can pass on the unfixed code, which is the 0.2.0 trap the spec itself describes. Fix: state the required environment (authenticated kiro-cli, bridged extension installed in pi's agent home), and assert `bridge.serve` in the first case's trace.
- [D5] "- Target release: pi-kiro-agent 0.4.1 (patch)": no reason is given against the bump table in `docs/releasing.md`. Fix: say why this is a patch (a bug fix that changes nothing a user types or sets, and moves no floor).
- [D5] "CHANGELOG `## 0.4.1` → `### Fixed`": `CHANGELOG.md` already has a `## Unreleased` section with two `### Fixed` bullets (#58), and `docs/releasing.md` step 4 cuts a release by renaming `## Unreleased`. The spec does not say whether 0.4.1 ships those entries or where the new bullet goes until the cut. Fix: say that the bullet goes under `## Unreleased` → `### Fixed` and that the 0.4.1 cut renames that section, #58 entries included.
