## Findings
- [D1] "The bridge probably holds the loop open.": the cause is hedged even though the spec's own evidence settles it: the 30 s `getActiveResourcesInfo()` snapshot shows `TCPServerWrap` as the only active handle, on the port the `bridge.serve` trace reported, and the `PI_KIRO_BRIDGE=off` control exits 0. Fix: state the cause as established (the referenced listener created by `httpServer.listen(0, "127.0.0.1", ...)` in `serveBridgeHttp()` is the sole remaining loop reference) and cite the snapshot and the bridge-off control as the proof, dropping "probably" and "likely".
- [D1] "The bug was latent in 0.3.0, where ACP was opt-in, and became visible when 0.4.0 made ACP the default.": provenance is given by version but not by commit. Fix: cite 6ea0510 (bridge lifetime moved to the child via `childAbort`, so the listener outlives the turn; in v0.3.0) and 791cab9 (ACP made the default; v0.4.0).
- [D2] "Today the referenced bridge listener holds the loop open through that wait.": this holds only when a bridge is mounted. With `PI_KIRO_BRIDGE=off`, or no capturable tools (`serveBridgeHttp()` returns `undefined`), plus workflow MCP servers from `discoverWorkflowMcpServers()`, nothing holds the loop during the `server_initialized` wait even before this change. The spec does not argue this context, and does not say whether the new startup-gate keepalive also fixes it or whether it should be tested. Fix: argue the bridge-off/no-tools plus workflow-server context, and add a startup-gate test case with no bridge server.
- [D3] "`docs/design/acp-transport.md` §5e.3": the spec does not cite §5 (Risks & open questions) of the same design doc. Its risk table already lists "Host process cannot exit after a one-shot turn" with `setChildKeepalive` as the full mitigation, and this spec shows that mitigation is incomplete. Fix: cite §5 and say that its row will be updated to cover the bridge listener and the startup gate.
- [D4] "spawn the real `pi -p` with ACP and the bridge enabled.": the live test does not say how the spawned `pi` loads this working tree's extension, not an installed pi-kiro-agent 0.4.0. It also does not list what else it needs (a `pi` binary on PATH, an authenticated kiro-cli seat, network). Without that, the negative/positive run may be testing the wrong code. Fix: name the load mechanism (for example an explicit extension path pointing at `src/index.ts`) and the required environment, alongside the strip list.
- [D5] "Target release: pi-kiro-agent 0.4.1 (patch)": the bump is stated but not justified against the table in `docs/releasing.md`. Fix: add the reason (a bug fix that changes no user-visible surface, `PI_KIRO_*` meaning or floor, so a patch), and note that the cut also ships the items already under `## Unreleased`.
