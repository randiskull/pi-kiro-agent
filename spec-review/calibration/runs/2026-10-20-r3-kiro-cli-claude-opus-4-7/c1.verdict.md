## Findings
- [G1] "Then remove the resume branch of `resolveSession()`, so every turn takes the divergence branch: it retires the session, mounts a fresh bridge through `ensureChildBridge()`, and advertises the new URL to kiro in that turn's `session/new`.": the spec names interactive sessions as a case that must "behave as before", but on turn 2+ of an interactive session a bridged tool call now has to reach a bridge whose URL changed since the first session/new. §5e.3's live receipts record that kiro keeps the MCP client it built for the server named `pi` pointed at the first URL and does not rebuild it on a successor session/new, which is the mechanism the one-URL-per-child invariant exists to work around; the Approach removes that invariant for the named case without saying what replaces it or why the case cannot arise, so the behaviour on every turn after the first is decided nowhere. Fix: decide the case — either keep the per-child mount (the unref alone covers the hang, as the Root cause already argues) and drop the per-turn close/remount, or spell out concretely how kiro's existing MCP client is forced to adopt each turn's new ephemeral URL (and pin it with a multi-turn live test, not just the one-shot in criterion 2).
- [D2] "The per-child bridge URL invariant (§5e.3) is preserved.": asserted in Goal item 3, not argued for the mechanism the Approach actually adds. The Approach closes the server at every `session/prompt` settle, clears `entry.bridgePromise`, and sends `session/new` with a new URL on the next turn — a context (second and later turns of an interactive session) that the change obviously reaches, where §5e.3 is the exact invariant at stake, is not considered. Fix: argue the invariant for every turn, with a reference to how kiro's MCP client is reused across session/new on one child, or revise the Approach so no new URL is ever advertised to a long-lived kiro child.
- [D3] "Also close the bridge when a turn settles, so a listener can never outlive the turn that needed it, even if a later change refs it again.": overturns the "one bridge URL per child across a session reset" decision in `docs/design/acp-transport.md` §5e.3 (and in 6ea0510, which the Root cause itself cites as the fix that established that invariant), and contradicts the spec's own `### Out of scope` item that reads "Changing the idle-timeout default or the bridge URL lifetime model. Unchanged, no follow-up: the unref fixes the hang without touching either." The Approach moves bridge lifetime from child-scoped to turn-scoped (close at turn settle, remount with a new port on the next turn, resume branch removed) while claiming to preserve the opposite. Fix: drop the per-turn close + resume-branch removal and keep only the unref plus the startup-gate ref change — the Root cause's own analysis says the unref alone resolves the hang. If a per-turn bridge is genuinely wanted, promote this to a supersede of §5e.3 with its own argument and move the item out of `### Out of scope`.
