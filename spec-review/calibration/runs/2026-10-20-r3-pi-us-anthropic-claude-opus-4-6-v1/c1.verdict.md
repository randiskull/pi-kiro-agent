## Findings

- [G1] "Then remove the resume branch of resolveSession(), so every turn takes the divergence branch": the change removes the code path that existing callers rely on when `planAcpTurn` returns `mode: "resume"`. The prompt-building branch at line 1210 (`useResume ? buildDeltaPrompt(...) : buildPromptFromContext(...)`) and the session-recording branch at line 1277 (`if (useResume && plan.acpSessionId) { advanceAcpSession(...) }`) still key on `useResume`, which `planAcpTurn` still sets to `true` for a prefix-matching multi-turn. After the resume branch is removed, a "resume"-planned turn hits the divergence path (fresh `session/new`, dropped `acpSessionId`), but the prompt is built as a delta (only new messages) for a kiro session with no history, and `advanceAcpSession` operates on the dropped session id, so the new session is never recorded. The spec does not decide what these two branches do after the resume path is gone. Fix: either keep the resume branch (the `unref` alone fixes the one-shot hang, and the bridge close can be scoped to non-resume exits) or explicitly adjust the prompt-building and session-recording logic to match the all-divergence model and state what interactive multi-turn behaviour becomes.

- [G1] "Interactive sessions, `/new`, `/resume`, `fork` and `reload` behave as before": the Goal names this case but nothing in the Approach or any other section says what the change does for an interactive multi-turn session that would have resumed. Removing the resume branch and closing the bridge per turn means every interactive turn creates a fresh kiro session and a fresh bridge URL; conversation continuity within kiro is lost. The effect on the user is undecided. Fix: decide and state the interactive-mode behaviour — either preserve resume (scope the bridge close to the one-shot exit path) or acknowledge the loss of intra-kiro continuity and argue why it is acceptable (e.g. because pi replays the full prefix anyway when `planAcpTurn` falls through to "fresh" on the next turn).

- [G2] "docs/specs/dual-host-pi-gsd.md": the path does not exist at the ref — `docs/specs/` is absent from the repository. Fix: commit the file before or alongside this spec, or mark it `(new)` and have the Approach create it; alternatively cite the sibling spec by its actual committed path or issue number.

- [D3] "The per-child bridge URL invariant (§5e.3) is preserved": the Goal claims this, but the Approach says "close the bridge when each turn settles… mount a fresh one for the next turn" and "every turn takes the divergence branch: it retires the session, mounts a fresh bridge through ensureChildBridge(), and advertises the new URL to kiro in that turn's session/new." This explicitly breaks the §5e.3 invariant, which the design doc states as "from kiro's point of view the bridge URL is a property of the child, fixed when the child first learns it" (docs/design/acp-transport.md line 475 ff.). Acceptance criterion 4 further claims "The §5e.3 tests (one URL per child across a session reset) pass unchanged," but a per-turn bridge remount would produce a different URL each turn, failing the test that asserts one mount per child. Fix: reconcile Goal and Approach — either preserve §5e.3 (unref alone, keep the bridge child-scoped) or supersede §5e.3 with a per-turn bridge model, update the design doc, rewrite the Goal claim, and adjust the §5e.3 test expectation.

- [D2] "Interactive pi keeps its own references (TTY and stdin), so it is unaffected": this argues the process-exit invariant for interactive mode but does not argue the session-continuity invariant. The close-per-turn and remove-resume changes reach interactive mode (resolveSession and the bridge lifecycle are shared code paths), and the safety of losing intra-kiro history between turns is not considered. Fix: add an argument for the interactive context — either that continuity is preserved (by keeping the resume branch) or that losing it is safe (because pi replays the full message prefix on a fresh session).
