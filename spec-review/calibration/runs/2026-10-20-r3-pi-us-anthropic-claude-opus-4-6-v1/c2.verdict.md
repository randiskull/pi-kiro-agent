## Findings

- [G1] "Mechanics (pick the lightest that satisfies Step 0):": The spec offers two alternative wiring mechanisms — a `package.json` with `pi.extensions` pointing at the built entry, or a one-line `index.ts` that re-exports the default factory — and hands the choice to the implementer rather than selecting one. Both the test fixture and the user-facing documentation depend on which is built. Fix: pick one mechanic and specify it; the other can be noted as a rejected alternative.

- [G1] "Create a subdirectory under a GSD extensions root — `~/.gsd/agent/extensions/pi-kiro/` (global) or `<project>/.gsd/extensions/pi-kiro/` (project-local)": The placement (global vs project-local) is left open. The test needs one layout to exercise, and the documentation recommends one to users. Fix: select one as the primary documented path; the other can be mentioned as an alternative but the spec must say which the test exercises and which the docs lead with.

- [G1] "Do not throw at module top level if a pi-only global/singleton is absent under GSD; detect host capabilities and degrade (skip a bare-pi-only convenience) rather than failing the whole load.": Option C introduces degrade behaviour as work to be done, but does not identify which pi-only global or singleton is at risk or what is skipped when it is absent. The spec's own Step 0 Q3 says the factory shape and manifest field are "already satisfied," so either there is nothing to guard against (in which case Option C is a no-op and should say so) or there is a specific surface (in which case the spec must name it and decide the degrade path). Fix: audit the module-level and factory-level imports for GSD-absent surfaces; name each one or state that none exist.

- [G4] "Under a GSD home, loading pi-kiro-agent does not alter or break GSD's own extension set (GSD's bundled extensions still load; the cmux message, if any, is GSD-pre-existing and unchanged by this package).": This is a behaviour criterion — "GSD's bundled extensions still load" is something a program does — and no Verification plan step produces evidence for it. Fix: either add a verification step that loads the wiring alongside a representative GSD extension set and asserts all load, or demote the criterion to a documentation assertion ("the wiring adds a subdirectory and touches no existing file") with a named file as evidence.

- [G5] "The transport/parsing internals (ACP vs chat) - unaffected by host scoping.": "Unaffected" describes the item's current state (a reason) but is not a disposition. The rubric requires "dropped", "unchanged", "no follow-up", or a named spec/issue/owner. Fix: replace "unaffected by host scoping" with "unchanged, no follow-up" (or another valid disposition).

- [D1] "## Root cause": The mechanism is traced to code (GSD's separate extension discovery path, pi-kiro-agent installed only under pi's home) and control observations rule out alternatives (bare pi lists the models, cmux error is independent). However, no commit provenance is given for when the gap was introduced. Fix: cite the commit that first installed pi-kiro-agent under pi's home (or the earliest commit where GSD support could have been expected), or state that the gap has existed since initial packaging and cite that commit.

- [D2] "Under a GSD home, loading pi-kiro-agent does not alter or break GSD's own extension set": The invariant is asserted but not tied to any test that would catch its breakage. The factory-shape assertion covers the load-error invariant, and the bare-pi e2e covers the regression invariant, but nothing tests the non-interference invariant. Fix: tie the non-interference claim to a specific test (even a structural argument — "the wiring adds a new subdirectory and imports nothing from GSD's existing extensions" — coupled with a test that the wiring dir contains only the expected files).

- [D3] "## Acceptance criteria": The spec does not cite `docs/releasing.md`, which is relevant: the change adds user-visible capability (kiro models under GSD) and the releasing doc's table says that is at least a minor bump. The version decision is entirely absent. Fix: cite `docs/releasing.md`, state the target version per its table, and name the CHANGELOG section.

- [D4] "before the fix, add the GSD-home load test and confirm it fails (provider not registered / load error)": The spec's own Step 0 Q3 says the factory shape and manifest are "Already satisfied by this repo," and no specific pi-only surface that would throw is identified. If the GSD-home load test creates the wiring subdirectory (which it must, to test the wiring), the extension would load successfully even before any code change, making the negative control pass on both sides. Fix: identify the specific code change that makes the test transition from fail to pass, or redesign the negative control so the "before" run omits the wiring and the "after" run includes it, with an explicit statement of which side is which.

- [D5] "## Acceptance criteria": None of the four D5 items are present. No target version is chosen per `docs/releasing.md`. No CHANGELOG section or subsection is named. No workaround is offered for users on affected released versions (the wiring is the fix, but framing it as a workaround available today is absent). No rollback or migration is discussed. Fix: add a target version with the reason per `docs/releasing.md`'s table (this is user-visible capability, so at least minor); name the CHANGELOG section and `### Added` or `### Fixed` subsection with a bullet citing its test; state the manual wiring as a workaround available on any current version; state that no persistent state is changed so rollback is a removal of the wiring subdirectory.
