## Findings

- [G1] "remove the resume branch of resolveSession(), so every turn takes the divergence branch: it retires the session, mounts a fresh bridge through ensureChildBridge(), and advertises the new URL to kiro in that turn's session/new": The behaviour of bridged tool calls in the second and subsequent turns of an interactive session is undecided. The approach closes the bridge after each turn, clears `entry.bridge` and `entry.bridgePromise`, and forces every turn through the divergence branch, which mounts a fresh bridge on a new ephemeral port. The spec's own cited evidence (§5e.3 in `docs/design/acp-transport.md`) demonstrates that kiro does not learn a new bridge URL from a subsequent `session/new` on the same child — "kiro accepts the new session but keeps the MCP client it already built for the server named `pi`, still pointed at the closed port." No mechanism is decided for how bridged tool calls would reach the new port. Fix: either scope the per-turn bridge close to one-shot mode only (where there is no second turn), or drop the per-turn close and resume-branch removal entirely and rely on the `httpServer.unref()` as the sole fix, or explain why the §5e.3 limitation no longer applies and what replaces the per-child bridge invariant.

- [D3] "Interactive sessions, /new, /resume, fork and reload behave as before. The per-child bridge URL invariant (§5e.3) is preserved.": Goal item 3 claims the §5e.3 invariant (one bridge URL per child, mounted once, reused across sessions) is preserved, while the Approach removes session reuse and mounts a new bridge per turn — directly undoing the §5e.3 fix. The §5e.3 design doc section states: "The bridge is mounted once (`acpEntry.bridge ??= …`) and both the new-session and divergence branches reuse it; divergence keeps retiring `sessionAbort` and no longer touches the server." The Approach does the opposite: it closes the server at turn end and mounts a replacement. Fix: reconcile the Goal with the Approach — either preserve §5e.3 by keeping the bridge per-child and not removing the resume branch, or acknowledge that §5e.3 is superseded, explain why kiro will now honour the new URL, and update Goal 3.

- [D3] "The §5e.3 tests (one URL per child across a session reset) pass unchanged": The existing §5e.3 test (`test/acp-transport.test.ts`, "keeps one bridge URL across a divergence reset, so kiro never calls a dead port") asserts: (a) both sessions receive the same URL (`expect(urlsPerSession[1]).toBe(urlsPerSession[0])`), (b) exactly one bridge mount for the life of the child (`expect(calls).toHaveLength(1)`), and (c) the bridge is never closed (`expect(calls[0].close).not.toHaveBeenCalled()`). The Approach — close the bridge per turn, clear `bridgePromise`, and mount a fresh one — would fail all three assertions. The acceptance criterion claims the test passes unchanged; the approach makes it fail. Fix: either drop the per-turn close so the test passes as claimed, or rewrite AC 4 and the §5e.3 test to match the new per-turn model.

- [D2] "## Approach": The safety argument ("Why this is safe") covers the `httpServer.unref()` across four contexts (mid-turn, bridged calls, chat transport, interactive pi) and the startup-gate hold. It does not argue for the per-turn bridge close and resume-branch removal in multi-turn interactive sessions with bridged tools — a context the change obviously reaches, since `resolveSession` is shared by one-shot and interactive paths. Fix: either add a safety argument for the multi-turn interactive path under the new per-turn bridge lifecycle, or remove the per-turn close and resume-branch removal from the approach.

- [D5] "Target release: pi-kiro-agent 0.4.1 (patch)": The version is named and the bump type is stated, but the reason it is a patch per the `docs/releasing.md` table is not given explicitly. Fix: state that the change is a bug fix with no user-visible surface change, matching the patch row in the releasing table.
