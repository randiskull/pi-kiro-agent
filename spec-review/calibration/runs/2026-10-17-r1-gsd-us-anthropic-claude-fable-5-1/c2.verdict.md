## Findings
- [G1] "Mechanics (pick the lightest that satisfies Step 0):": the wiring that is the whole deliverable is left as a choice between a `package.json` with `pi.extensions` and a one-line `index.ts` re-export, and between a global and a project-local root, handed to the implementer. Fix: decide one mechanism and one root (or state both are documented and which the test exercises), and give the exact file content the docs will carry.
- [G1] "export { default } from \"pi-kiro-agent\";": the spec does not say how GSD's jiti resolves the bare specifier `pi-kiro-agent` from a wiring directory that has no `node_modules` (absolute path to `~/.pi/agent/npm/node_modules/pi-kiro-agent`, a symlink, a local `npm install`), so the one concrete artefact offered is unresolvable as written. Fix: state the resolution path the wiring relies on and the exact specifier or path the docs will tell users to write.
- [G1] "detect host capabilities and degrade (skip a bare-pi-only convenience) rather than failing the whole load": a degrade path that does not name which capability is detected or what is skipped. Fix: name the pi-only surface(s) `src/index.ts` touches at load, the probe used, and the exact behaviour dropped under GSD; or state that no such surface exists and delete the bullet.
- [G2] "GSD **never scans `npm/node_modules`** for extensions, so there is nothing resembling `pi install npm:pi-kiro-agent` into GSD's home": the installed build contradicts this. `packages/pi-coding-agent/dist/core/package-manager.js` (`getManagedNpmInstallPath` -> `<agentDir>/npm/node_modules/<name>`, `resolve()` reading `settings.packages`) and `dist/core/package-commands.js` (`gsd install npm:@foo/bar`) show a package-install path; `discoverAndLoadExtensions` is only the directory half, the CLI loads via `ResourceLoader` -> `packageManager.resolve()`. Fix: re-verify Q1 against `package-manager.js` and `resource-loader.js`, and either restore Option A (`gsd install npm:pi-kiro-agent`, with the `@earendil-works/*` import question answered) or state precisely why it does not work.
- [G2] "host identity is `.../config.js` + `dist/app-paths.js`": no `app-paths.js` exists anywhere under `@opengsd/gsd-pi` v1.22.0 (`find ... -name "app-paths*"` returns nothing); `getAgentDir`, `ENV_AGENT_DIR` and `CONFIG_DIR_NAME` all live in `dist/config.js`. Fix: drop the `app-paths.js` citation or cite the file that actually holds the symbol.
- [G2] "Negative control first (per repo engineering rule)": no such rule exists in the repo (no match for negative control in README, CONTRIBUTORS, docs/, .github/, .kiro/). Fix: cite the file and heading that states the rule, or remove the attribution and just state the control.
- [G2] "**ASCII-only** in any host-read string (manifest fields, extension name, command ids) per repo convention": no such convention is written anywhere in the checkout. Fix: cite the document that states it, or present it as a decision this spec makes.
- [G2] "the installed build is newer than the v1.2/v1.3 referenced in older steering notes": the notes are not named, so the version claim cannot be checked. Fix: name the file (or drop the sentence; the versioned statement against v1.22.0 stands on its own).
- [G3] "before the fix, add the GSD-home load test and confirm it **fails** (provider not registered / load error). It must fail for the right reason": the spec's own Q3 says the factory shape and manifest are already GSD-compatible, and the fix is a documented manual wiring step plus docs, so a test that itself creates the `extensions/pi-kiro/` wiring under a temp agent home passes on the unchanged code; the two offered reasons are alternatives, not a mechanism, and neither follows from what the change actually alters. Fix: state exactly what the pre-change run lacks (for example: with no wiring subdirectory, `discoverAndLoadExtensions` under `GSD_CODING_AGENT_DIR=<tmp>` yields zero extensions and no `kiro` provider) and what single code or fixture change flips it, so the test fails for the defect and not for a fixture error.
- [G4] "Under a GSD home, loading pi-kiro-agent does not alter or break GSD's own extension set (GSD's bundled extensions still load": no Verification plan step loads GSD's bundled extensions alongside pi-kiro-agent, so nothing produces evidence for this criterion. Fix: add a step (e.g. load a fixture GSD `extensions/` set plus the wiring through the same discovery call and assert the bundled count and names are unchanged), or drop the criterion.
- [G4] "a one-shot turn against `kiro/auto` completes (the spike's failing command, now passing). Evidence: captured command output.": the spike's command is never written down, so the evidence has no stated form. Fix: give the exact `gsd`/`pi` invocation (binary, flags, agent-dir env) and the output lines to capture.
- [D2] "Loading the extension under either host must not raise errors or interfere with the other host's extension set.": safety is asserted; the spec never argues the one context the change obviously reaches. `src/acp-transport.ts`, `src/stream-adapter.ts` and `src/system-prompt.ts` import `@earendil-works/pi-ai` at runtime, which pi's loader virtualises but GSD's loader (`loader.js` aliases only `@gsd/*`) does not, so under GSD the re-exported module throws at import unless something supplies that package. Fix: name the invariants (module resolution of the two peer deps, provider name uniqueness, no write into `~/.gsd/agent/`, kiro-cli subprocess lifetime), argue each under GSD, and tie each to the GSD-home test.
- [D3] "there is no package-install mechanism to lean on": `docs/design/acp-transport.md` ("GSD's own agent (`~/.gsd/agent/settings.json`) runs a Bedrock model with `packages: []` and so never loads pi-kiro") already records that GSD's `packages` setting is the mechanism by which pi-kiro would be loaded, which this spec contradicts without citing or superseding it. Fix: cite that section, reconcile Q1 with it, and state whether `settings.packages` is now the recommended enable path.
- [D3] "selected via `GSD_CODING_AGENT_DIR` / `GSD_HOME`": the Goal names `GSD_HOME` as a selector, Step 0 Q1 says `getAgentDir()` reads only `GSD_CODING_AGENT_DIR` else `~/.gsd/agent`, and `src/workflow-mcp-discovery.ts` in this repo reads `GSD_HOME`; the spec does not reconcile the three. Fix: state which variable(s) the GSD loader honours at v1.22.0 and which this repo's own discovery honours, and make the test set the one the loader reads.
- [D4] "loads through GSD's documented discovery path": the repo's devDependency is `@earendil-works/pi-coding-agent`, and the spec does not say how the test obtains GSD's `discoverAndLoadExtensions` (a `@opengsd/gsd-pi` devDependency, the globally installed build, a vendored copy) or what it does when GSD is absent in CI. Fix: name the import source and version, and the skip or install behaviour when it is missing.
- [D4] "Live smoke (gated, `PI_KIRO_LIVE=1`)": the gate is named but the environment is not (GSD version, agent dir, a logged-in kiro-cli, what to strip). Fix: list the environment the step needs and the command it runs.
- [D5] "- Status: Draft (Step 0 verified)": no target version per `docs/releasing.md`, no CHANGELOG section or `### Fixed`/`### Added` bullet naming its test, no workaround for users on 0.4.0 (the manual wiring is itself the workaround and could be stated as such), no statement that nothing shipped changes if that is the position. Fix: add a release section covering target version with reason, the CHANGELOG line, and the workaround.
- [D6] "### Option C - Load-safety hardening (applies regardless)": a speculative code change to `src/index.ts` (host-capability detection and degrade) is interleaved with a docs-plus-wiring change and cannot be reviewed apart, since the spec itself finds the factory shape already correct. Fix: either drop Option C to the factory-shape test only, or split it into a labelled separable commit with its own test.
