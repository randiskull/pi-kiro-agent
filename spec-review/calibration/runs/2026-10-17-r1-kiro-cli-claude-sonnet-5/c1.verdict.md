## Findings
- [G1] "Then remove the resume branch of `resolveSession()`, so every turn takes the divergence branch: it retires the session, mounts a fresh bridge through `ensureChildBridge()`, and advertises the new URL to kiro in that turn's `session/new`.": the spec never decides what happens to kiro's already-built MCP client for the server named `pi` when a second `session/new` on the same child advertises a new URL for it. The spec's own Root cause states kiro "learns the bridge URL only once, at session/new" and docs/design/acp-transport.md §5e.3 (cited by the spec itself) records that this exact sequence — close the bridge, mount a new one on a new port, call session/new with the new URL — left kiro's existing `pi`-server MCP client pointed at the dead port, failing every bridged call for the rest of the conversation. The Approach does not say why a fresh bridge/URL every turn would not reproduce that failure. Fix: either argue concretely why per-turn remount does not trigger the §5e.3 mechanism (e.g. because kiro treats a divergence-driven session/new differently from a mid-session reset), with evidence, or change the approach so the bridge port, once learned, is never changed for the life of the child (unref it instead of closing/remounting it).
- [D2] "The per-child bridge URL invariant (§5e.3) is preserved.": asserted, not argued. The Safety-argument bullets ("During a turn...", "Bridged calls arrive only mid-turn...", "Chat transport...", "Interactive pi...") never address the one context the change obviously reaches: a second turn on the same child, after the Approach's own "close the bridge when a turn settles... mount a fresh one for the next turn" takes effect. That is precisely the scenario §5e.3 diagnosed as broken. Fix: add an invariant argument for "the bridge URL kiro has already cached for server `pi` must not change while the child lives," tied to a test, covering the per-turn-close design specifically, not just the already-covered per-connection and per-session-reset cases.
- [D3] "4. **No regressions.** ... The §5e.3 tests (one URL per child across a session reset) pass unchanged.": contradicted by the cited test itself. test/acp-transport.test.ts, "keeps one bridge URL across a divergence reset, so kiro never calls a dead port" asserts `expect(calls).toHaveLength(1)` and `expect(calls[0].close).not.toHaveBeenCalled()` across two turns on one child (the second one taking the divergence branch). Under the spec's Approach — close the bridge at every turn's end and remove the resume branch so every subsequent turn takes the divergence branch and calls `ensureChildBridge()` again after `bridgePromise` was cleared — the second turn in that same test would mount a second bridge and would call close() on the first, making both assertions fail. The spec asserts this test is unaffected without reconciling that its own described change rewrites the exact behavior the test pins. Fix: either update the test's expectations (and say so, since it changes a documented regression gate) or revise the Approach so it genuinely does not touch per-child bridge reuse.
- [G1] "Also close the bridge when a turn settles, so a listener can never outlive the turn that needed it, even if a later change refs it again.": the rationale "even if a later change refs it again" defends against a different, hypothetical risk (a future ref leak) while silently incurring a present, evidenced one (kiro calling a dead URL per §5e.3). The contract for what happens to in-flight state kiro holds about the old bridge is left undecided — this is the open-choice pattern G1 fails on ("a degrade or fallback path that does not say what is skipped"), not merely a missing citation.
