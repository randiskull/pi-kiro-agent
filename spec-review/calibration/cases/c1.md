# Implementation Spec: `pi -p` must exit after a kiro turn on the ACP transport (0.4.1)

- Status: Draft
- Area: ACP transport / process lifetime
- Target release: pi-kiro-agent 0.4.1 (patch)
- Related: `src/bridge.ts`, `src/acp-transport.ts`, `src/index.ts`,
  `docs/design/acp-transport.md` §5e.3,
  `.gsd/workflows/spikes/261017-1-spike/research/ANGLE-5.md` (investigation)

## Goal

A one-shot host (`pi -p`, GSD headless, any print-mode or scripted run) that
completes a kiro turn on the default ACP transport must exit as soon as the
turn ends. It must not stay alive until the ACP idle timer (10 min) kills the
child.

After this change:

1. `pi -p --model kiro/<id> "<prompt>"` exits 0 promptly after printing the
   answer, with the tool bridge enabled (the default).
2. A turn that calls a bridged pi tool still works end to end.
3. Interactive sessions, `/new`, `/resume`, `fork` and `reload` behave as
   before. The per-child bridge URL invariant (§5e.3) is preserved.

## Observed failure

0.4.0 made ACP the default transport. With it:

| Run | Result |
|---|---|
| `pi -p --no-session --model kiro/auto "Reply: x"` | answer printed, then hangs; killed by the 240 s `timeout` |
| same, `PI_KIRO_TRANSPORT=chat` | exit 0, 10.5 s |
| same, `PI_KIRO_BRIDGE=off` | exit 0, 9.3 s |
| same session, `amazon-bedrock/...` | exits normally |

A preload snapshot of `process.getActiveResourcesInfo()` in the `pi` process,
30 s after the answer printed:

```
resources: ["TCPServerWrap"]
Server listening {"address":"127.0.0.1","port":65238}   <- matches the bridge.serve trace port
```

The only active handle is the tool bridge's loopback HTTP server.

## Root cause

- `setChildKeepalive()` (`src/acp-transport.ts`) deliberately `unref()`s the
  ACP child and its three stdio pipes whenever no request is in flight, so
  that "a one-shot host must be able to exit".
  `test/acp-transport.test.ts` ("event-loop keepalive") pins this.
- The bridge server is meant to outlive the turn, and has been since 2303d19
  first mounted it on the ACP transport, documented as per-session. Until
  d47b48e (#35) it rode the turn's AbortSignal, which pi never aborts when a
  run completes (`runWithLifecycle()` and `finishRun()` in
  `node_modules/@earendil-works/pi-agent-core/dist/agent.js`, 1.3.0). d47b48e
  bound it to the session's `sessionAbort`, and 6ea0510 (v0.3.0) moved it to
  the **child** (`childAbort`), because kiro learns the bridge URL only once,
  at `session/new`. A one-shot run ends none of the three before it exits, so
  the listener is still open after the answer, and `serveBridgeHttp()` never
  `unref()`s it (`src/bridge.ts`, after
  `httpServer.listen(0, "127.0.0.1", ...)`). That one reference undoes the
  keepalive design. 6ea0510 widened the window; it did not open it.
- The 0.2.0 live check of the keepalive fix does not contradict this. 8ec09e2
  (CHANGELOG `## 0.2.0`: "15.5s clean exit with the fix") ran with a clean
  agent home, per its commit message. A clean home installs none of the
  extensions whose tools are bridged, and with no tools `serveBridgeHttp()`
  returns `undefined` and listens on nothing.
- Nothing closes it before the idle timer: `src/index.ts` has no
  `session_shutdown` handler, and nothing on the one-shot exit path
  calls `teardownChild()`. Its callers are abort, idle timeout, the turn
  ceiling, a stale child, child exit, eviction (max children), a failed
  initialize and the test reset.
- The bug was latent in 0.3.0, where ACP was opt-in, and became visible when
  0.4.0 made ACP the default.

## Scope

### In scope
- Unref the bridge's listening server.
- Close the bridge when each turn settles, and mount a fresh one for the next turn.
- Keep the ACP child referenced through the session startup gate.
- Unit, regression and live tests (below).
- CHANGELOG entry, version bump to 0.4.1.

### Out of scope
- Credit-metering rebuild on `session_start`. Follow-up spec, owner: the
  maintainer. The same spike recommends it
  (`.gsd/workflows/spikes/261017-1-spike/RECOMMENDATION.md`, gitignored, local):
  rebuild the credit totals from the session entries on `session_start`, so the
  `kiro-credits` footer agrees with pi's own after `/resume`, `reload` or fork.
- Host scoping for GSD (`docs/specs/dual-host-pi-gsd.md`).
- Changing the idle-timeout default or the bridge URL lifetime model.
  Unchanged, no follow-up: the unref fixes the hang without touching either.
- Tearing ACP children down on `session_shutdown`. No follow-up: it is not
  needed, and it is not safe.
  - Not needed: `spawnAcpChild()` registers every child with
    `registerChildForCleanup()` (`src/acp-transport.ts`), whose `exit` hook
    SIGTERMs it, or its process group when detached, on an orderly exit
    (`src/orphan-reaper.ts`). Once the unref lets a one-shot host exit, its
    children go with it.
  - Not safe: the event is per session, not per host. pi reuses a loaded
    extension's factory for every session in the same cwd (`extensionCache` in
    `node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/loader.js`,
    pi-coding-agent 1.3.0), so those sessions share this module's child
    registry, and `@tintinweb/pi-subagents` 0.22.0 emits
    `session_shutdown` with `reason: "quit"` for each subagent session it
    disposes (`shutdownChildSession()` in
    `@tintinweb/pi-subagents/src/agent-manager.ts`). A registry-wide teardown
    there would kill the parent's child mid-turn.

## Approach

### Unref the bridge server

In `serveBridgeHttp()`, right after `listen()` resolves:

```ts
// The server lives as long as the ACP child (§5e.3), and the child is
// unref'd between turns so a one-shot host can exit (setChildKeepalive). A
// referenced listener would undo that. Unref only drops the event-loop hold:
// the server still accepts connections, and its lifetime is still owned by
// `signal` and close().
httpServer.unref();
```

Why this is safe:
- **During a turn**, `setChildKeepalive(true)` refs the child and its pipes,
  and the turn's awaited request is resolved from stdout, so the loop stays alive.
- **Bridged calls arrive only mid-turn.** Each accepted connection is its own
  referenced socket for its lifetime, so an in-flight tool call keeps the
  process up until it is answered.
- **Chat transport:** the bridge is per turn and closes with the turn, and the
  `kiro-cli chat` child stays referenced while it runs. Unref changes nothing there.
- **Interactive pi** keeps its own references (TTY and stdin), so it is unaffected.

Also close the bridge when a turn settles, so a listener can never outlive
the turn that needed it, even if a later change refs it again. When a turn's
`session/prompt` request settles, call `entry.bridge?.close("turn-end")` and
clear both `entry.bridge` and `entry.bridgePromise`. Then remove the
resume branch of `resolveSession()`, so every turn takes the divergence
branch: it retires the session, mounts a fresh bridge through
`ensureChildBridge()`, and advertises the new URL to kiro in that turn's
`session/new`.
Do not unref per connection.

The unref exposes one wait that the referenced listener used to cover. In
`startSession()`, the `session/new` response settles the last pending request,
so `dispatchMessage()` unrefs the child and its pipes; the function then waits
for `server_initialized` and `commands/available` while kiro starts its MCP
servers, with an unref'd timeout. Today the referenced bridge listener holds
the loop open through that wait. After the unref nothing would, so hold it
explicitly: call `setChildKeepalive(entry, true)` once `session/new` resolves,
and `setChildKeepalive(entry, entry.pending.size > 0)` in the existing
`finally`.

## Acceptance criteria

1. **Hang fixed.** With the default transport (ACP) and bridge enabled,
   `pi -p --no-session --model kiro/auto "Reply with just: ok"` exits 0. On the
   reference machine that took about 11 s. It passes when it exits 0 within
   120 s, the live test's bound, well under the 10 min idle timeout.
   Evidence: captured command, wall time and exit code.
2. **Bridged tool still works.** A `pi -p` turn that calls a bridged tool
   (`rpiv_todo` or any `pi` MCP tool) completes, trace shows `bridge.call` and
   `bridge.result`, exit 0. The spike measured 15.8 s.
3. **Unit: server unref'd.** `serveBridgeHttp()` returns a handle whose
   listening server does not keep the loop alive. The test passes at least one
   tool: with none, it returns `undefined` and listens on nothing. The child
   stays referenced from the `session/new` response until the startup gate
   settles, and is unreferenced after it. After a turn settles the child's
   bridge is closed, and the next turn mounts a new one.
4. **No regressions.**
   - The existing "event-loop keepalive" tests pass unchanged.
   - The §5e.3 tests (one URL per child across a session reset) pass unchanged.
   - `test/extension-load.e2e.test.ts` passes.
5. `npm run verify` passes.
6. CHANGELOG `## 0.4.1` → `### Fixed` describes the symptom, the cause and the
   workaround for 0.4.0 users (`PI_KIRO_TRANSPORT=chat` or `PI_KIRO_BRIDGE=off`).
   The bullet cites the criterion 3 test by file and test name, as
   `docs/releasing.md` requires of a `### Fixed` bullet. `package.json` is 0.4.1.

## Verification plan

- **Negative control first.** Write the unit test for criterion 3 and confirm
  it fails on the current `bridge.ts`, for the right reason (the handle is
  referenced). Then apply the fix and confirm it passes. Do the same for the
  startup-gate test below: on the current `startSession()` it fails because the
  child is unreferenced as soon as `session/new` is answered.
  - Preferred assertion: start the server inside a child `node` process that
    calls `serveBridgeHttp()` and does nothing else, then assert the child exits
    on its own within a few seconds. This exercises real event-loop semantics
    with no mocks.
  - Cheaper complement: spy on `Server.prototype.unref`, or check
    `process.getActiveResourcesInfo()` before and after.
- **Startup gate:** with a fake child and the `refOps` spy, answer
  `session/new` and hold `server_initialized`. Assert the child is referenced
  until the gate settles and unreferenced after (criterion 3).
- **Per-turn bridge:** drive two turns on one fake child and assert that each
  mounted its own bridge and that the first was closed when its turn settled
  (criterion 3).
- **Live regression (gated `PI_KIRO_LIVE=1`, in `test/acp-transport-live.test.ts`):**
  spawn the real `pi -p` with ACP and the bridge enabled. Assert exit 0 within a
  bound well under the idle timeout (for example 120 s), and that stdout
  contains the reply. Second case: a prompt that forces one bridged tool call,
  run with `PI_KIRO_TRACE` set. Assert exit 0, the reply, and one `bridge.call`
  and one `bridge.result` event in the trace (criterion 2).
  - Run the subprocess with a clean environment (strip `GSD_*`,
    `PI_PACKAGE_DIR`) so the host resolves pi's own agent home.
    `PI_PACKAGE_DIR` overrides the package directory, and the `piConfig` in that
    directory's `package.json` names the config dir, so an inherited value can
    point pi at another host's agent home (pi-coding-agent 1.3.0, `getPackageDir`
    and `getAgentDir` in
    `node_modules/@earendil-works/pi-coding-agent/dist/config.js`). The
    spike's `pi` was bound to GSD's agent home (`dual-host-pi-gsd.md`); the
    strip list keeps either variable from doing that to the test.
- **Manual reproduction (record in the PR):** run the command from criterion 1
  before and after the change, with `PI_KIRO_TRACE` set, and quote the
  wall time and exit code.
- **Full suite last:** run `npm run verify` (typecheck, tests, secret scan) on
  the final tree and record its exit code in the PR (criteria 4 and 5).

## Risks and notes

- **Exit mid-turn.** If a future change makes a turn wait on something other
  than a referenced handle (for example a timer-only wait with the child
  unref'd), the process could exit mid-turn. The keepalive invariant (ref the
  child while `pending > 0`, and through the startup gate) is what prevents
  that; the startup-gate unit test and the live test cover it.
- **A bridged tool that spawns detached work** after returning its result is
  already not kept alive in chat mode. Behaviour is unchanged, but worth a line
  in the PR.
- **The 0.4.0 workaround** to document until users upgrade:
  `PI_KIRO_TRANSPORT=chat` (stream-json text path) or `PI_KIRO_BRIDGE=off`
  (no pi tools for kiro).
