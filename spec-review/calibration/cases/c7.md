# Implementation Spec: the stream-json reader draws no row for kiro's internal tool calls

- Status: Draft
- Area: chat transport / stream-json reader
- Target release: pi-kiro-agent 0.4.1 (patch), with the next release; no bump of
  its own. Patch per the table in `docs/releasing.md`: an internal change, where
  nothing a user types or sets changes meaning and no released route draws
  differently (Problem). No released version is affected, so there is no
  workaround to document.
- Related: `docs/design/v3-engine.md` §3.3, §3.7, §4 (R8, R9) and §5,
  `src/stream-json-reader.ts`, `src/identity.ts`, `test/stream-json.test.ts`,
  `test/stream-json-live.test.ts`, `test/painted-once.test.ts`,
  `probes/stream-json-2.32/`

## Problem

`docs/design/v3-engine.md` is the measured design for kiro-cli's v3 engine. Its
R8 asks that v3's internal tool calls draw no tool row while kiro's built-in
tools still do, and its R9 asks that three update kinds v3 adds draw nothing.
Neither depends on which engine is selected: both are about what the reader does
with a payload. This spec builds those two and nothing else.

No user can reach v3 today. `CHAT_ENGINE` in `src/identity.ts` is the constant
`"v2"` and `src/stream-adapter.ts` passes it as `--agent-engine`, so this change
alters nothing a released route draws. It makes the reader correct before the
engine becomes selectable, so that the spec which makes it selectable does not
also have to change how rows are drawn.

### Measured: what the reader does with v3's payloads today

At `68ffb40`, a throwaway vitest file in a scratch worktree (not committed)
drove `createStreamJsonReader()` directly with `engine: "v3"` and the two tool
calls the design doc records for kiro-cli 2.32.0 and KAS 0.66.43 (§3.3, §3.7).
The doc elides their ids and the file path ("b70c...", "tooluse_...",
".../note.txt"), so the script fills them in as `b70c`, `read1` and
`note.txt`. The doc records no body for the internal call's
`tool_call_update`, so the script sends a minimal completing one, and none for
the three update kinds, whose subtypes §3.3 counts, so they get minimal bodies
too (the reader dispatches on the subtype alone). It printed the rows and
stream events it produced:

```ts

const upd = (u: unknown) => line({ type: "sessionUpdate", data: { sessionId: "sess_1", update: u } });

// reader = createStreamJsonReader(output, stream, pushThinking, { engine: "v3", livePrefix: "live_" });
// reader.feed(v3); reader.end(); then print output.content's toolCall blocks, the pushed
// event types, and reader.result().
```

Run with `npx vitest run` on that file, it printed:

```
rows:   [{"id":"live_b70c","name":"kiro_unknown","arguments":{}},
         {"id":"live_read1","name":"kiro_unknown",
          "arguments":{"path":"note.txt","offset":null,"limit":null}}]
events: ["toolcall_start","toolcall_end","toolcall_start","toolcall_end"]
result: {"messageText":"OK","terminal":{"type":"runFinished","status":"success",
         "sessionId":"sess_1","finalText":"OK","finalTextTruncated":false},
         "sessionId":"sess_1"}
```

So, at this ref:

- **The internal call draws a row.** It is named `kiro_unknown`, with empty
  arguments, and announced like any other call. The cause is the `tool_call`
  case in `src/stream-json-reader.ts`: it calls `surfaceRow()` for every call
  that has a `toolCallId` and has not been seen, and `KiroUpdate` declares only
  `toolName` and `mcpServerName` under `_meta.kiro`, so the reader cannot see
  the `toolId` and `toolOrigin` fields that tell the two calls apart. On v3 that
  is one spurious row per turn, every turn (§3.3).
- **The real call draws its row** with its complete arguments. Its name is also
  `kiro_unknown`, because v3 sends no `toolName` (§3.7). That is R12, and it is
  out of scope here.
- **The three new update kinds draw nothing.** The `default` branch of the
  reader's `onUpdate` returns, so they never reach a row, the thinking feed or
  the answer. Nothing pins that: the existing test "ignores unknown event types
  and sessionUpdate subtypes" uses the subtype `plan`, not any of these three.

### Measured: what v2 sends in the same fields

Every v2 tool event committed in `probes/stream-json-2.32/`, counted at
`68ffb40`: `sessionUpdate` events whose subtype starts with `tool_call`, then
those carrying `_meta.kiro.toolId` or `_meta.kiro.toolOrigin`.

```sh
tools='select(.type=="sessionUpdate") | .data.update | select(.sessionUpdate | startswith("tool_call"))'
for f in probes/stream-json-2.32/*.jsonl; do
  n=$(jq -c "$tools" "$f" | wc -l)
  m=$(jq -c "$tools | select(._meta.kiro.toolId != null or ._meta.kiro.toolOrigin != null)" "$f" | wc -l)
  echo "$(basename "$f") $n $m"
done
```

```
capture                 tool events   with toolId or toolOrigin
p1-builtin.jsonl                  2                           0
p2-resume.jsonl                   0                           0
p2b-badresume.jsonl               0                           0
p3-toolerr.jsonl                  4                           0
p4-long.trimmed.jsonl             0                           0
p5-thought.jsonl                  0                           0
```

v2 identifies a call by `_meta.kiro.toolName` (`read`, `shell`), and several v2
updates carry `kind: null` and `_meta: null`
(`probes/stream-json-2.32/p3-toolerr.jsonl`). The design doc's §3.7 table
shows the distinguishing fields on v3: the internal call has `toolId` and no
`toolOrigin`, and the real call has `toolOrigin` `default` and no `toolId`.

## Goal

After this change, on any engine:

1. A `tool_call` or `tool_call_update` that carries a non-empty
   `_meta.kiro.toolId` and no `_meta.kiro.toolOrigin` is **internal**. It draws
   no row, emits no `toolcall_*` event and no thinking line, and is traced once
   per call id.
2. Every other call draws exactly what it draws today: the same rows, ids,
   names and arguments, on every committed v2 capture.
3. `available_commands_update`, `config_option_update` and
   `session_info_update` draw nothing, as today, and a test now fails if that
   changes.

## Scope

### In scope

- `src/stream-json-reader.ts`: `KiroUpdate`'s `_meta.kiro` gains
  `toolId?: string` and `toolOrigin?: string`; the exported predicate
  `isInternalToolCall()` (new); a per-turn set of hidden call ids; the
  `chat.stream.internal_tool_hidden` trace (new).
- `test/stream-json.test.ts`: the tests in the Verification plan.
- `docs/design/v3-engine.md`: §5's heading and R8, R9 status (Approach step 5).
- `CHANGELOG.md`: one `### Changed` bullet under `## Unreleased`.

### Out of scope

- **Naming v3's rows (R12).** Real v3 rows keep reading `kiro_unknown` after
  this change. Follow-up spec, owner: the maintainer. It needs S1's bridged-call
  payload first (§5), because a bridged tool's `title` is set by the MCP server.
- **Selecting the engine (R1, R2, R3, R11).** `CHAT_ENGINE` stays `"v2"`.
  Follow-up spec, owner: the maintainer, after S1, S3 and S5 (§5).
- **Metering on v3 (R4 to R7).** Follow-up spec, owner: the maintainer. The
  design's D1 recommends it as a blocker for R1, not for this change, which
  prices nothing.
- **The conformance suite's engine dimension (R10).** Goes to the R1 follow-up
  spec above, owner: the maintainer, because there is no v3 route to drive until
  the engine is selectable.
- **The ACP transport.** `src/acp-transport.ts` has its own update handler and
  runs only v2 (R-ACP). Unchanged, no follow-up from this spec: R-ACP owns it.

## Approach

1. **Widen the type.** `KiroUpdate._meta.kiro` becomes
   `{ toolName?: string; mcpServerName?: string; toolId?: string; toolOrigin?: string }`.
2. **Decide internal in one place.** Export `isInternalToolCall(update)` from
   `src/stream-json-reader.ts`: true exactly when `_meta.kiro.toolId` is a
   non-empty string and `_meta.kiro.toolOrigin` is `undefined`. A
   `toolOrigin` of any value, including an empty string, makes the call not
   internal. A call with neither field, which is every v2 call measured above,
   is not internal.
3. **Hide in the reader.** Keep a `hidden` set of call ids for the turn, beside
   `rows`.
   - `tool_call`: if the id is missing, return (unchanged). If the id is in
     `hidden` or `rows`, return. If `isInternalToolCall(update)`, add the id to
     `hidden`, trace, and return. Otherwise call `surfaceRow()` (unchanged).
   - `tool_call_update`: if the id is missing, return (unchanged). If the id is
     in `hidden`, return **before** any row lookup, so a later update for a
     hidden call never draws a row or a failed marker, whatever it carries. If
     there is no row for the id and `isInternalToolCall(update)`, add the id to
     `hidden`, trace, and return. Otherwise the existing path runs unchanged.
   - The trace is `trace("chat.stream.internal_tool_hidden", { toolCallId, toolId })`,
     written once per hidden id, the first time the id is seen.
4. **Pin R9 without changing code.** The `default` branch stays as it is. The
   new test in the Verification plan is what holds it.
5. **Narrow the design's gate, explicitly.** `docs/design/v3-engine.md` §5 is
   titled "Spikes that must land before any implementation". R8 and R9 depend
   on none of them: S1 is the bridge, S2 resume, S3 the metadata event, S4
   thinking, S5 the failure paths. This spec renames §5 to "Spikes that must
   land before the engine is selectable (R1, R11)", adds one sentence saying
   that R8 and R9 are engine-independent reader behaviour measured in 3.3 and
   3.7, and marks R8 and R9 built, naming their tests. It supersedes the old
   heading in the same PR rather than working around it. It also adds to R11
   that S1's bridged-call capture must be checked against
   `isInternalToolCall()` before the engine is selectable (Risks).

### Safety

The changed code runs in one place: the stream-json reader, used by the chat
transport when `chatFormat()` picks `stream-json`. The text format does not use
it, and ACP has its own handler (Out of scope).

- **No v2 row is hidden.** The predicate needs `toolId`. None of the six v2
  tool events committed in `probes/stream-json-2.32/` carries it, and neither
  does any field `KiroUpdate` declared before this change. The predicate does
  not key on `kind` or `_meta` being null, which v2 updates do carry. Tied to
  the replay test in the Verification plan and to the live test below.
- **A row is drawn exactly once or not at all.** A hidden call emits no
  `toolcall_start`, so it cannot be drawn twice or half-drawn, and a visible
  call's path is unchanged. Tied to `test/painted-once.test.ts`, unchanged.
- **A hidden call stays hidden.** A later update for a hidden id is dropped
  before any lookup. Tied to the hidden-update test.
- **Nothing pi keeps changes.** The reader's rows carry `LIVE_TOOL_ID_PREFIX`,
  and `src/stream-adapter.ts` sends the `done` and `error` messages with
  `stripLivePlaceholders(output.content)`, so no live row reaches the stored
  turn or the resume hash in `src/message-hash.ts`. End-of-turn reconciliation
  (`reconcileToolCalls()`) runs only on the text format, so it never looks for
  a hidden row. Hiding one changes the drawing, never the stored turn. Tied to
  the existing p1 replay test, which asserts the `done` message carries no
  `toolCall` block.

Don'ts:

- Do not key on the `title` text or on the value `fetch_cloud_config`. v3 can
  add internal tools, and §3.7 gives the field shape, not a list.
- Do not key on `kind === null` or `_meta === null`: v2 updates carry both.
- Do not touch `src/acp-transport.ts`.

## Acceptance criteria

1. **The internal call is hidden.** Driving the reader with the §3.7 internal
   `tool_call` and its update leaves `output.content` with no `toolCall` block
   for `b70c`, pushes no `toolcall_*` event and no thinking text for it, and,
   with `PI_KIRO_TRACE` set, writes exactly one `chat.stream.internal_tool_hidden`
   line with `{ toolCallId: "b70c", toolId: "fetch_cloud_config" }`. Evidence:
   the test in `test/stream-json.test.ts`, passing.
2. **The real v3 call is still drawn.** The §3.7 `Read File` payload yields
   exactly one row, id `<livePrefix>read1`, with `arguments` equal to its
   `rawInput`, and name `kiro_unknown` (R12 is out of scope). Evidence: the
   same describe block, passing.
3. **A hidden call stays hidden.** After the internal `tool_call`, a
   `tool_call_update` for `b70c` that carries `status: "failed"` and a
   `toolName` draws no row and no failed marker.
   Evidence: the hidden-update test, passing.
4. **v2 is unchanged.** `isInternalToolCall()` is false for every tool event in
   every capture in `probes/stream-json-2.32/`, and the existing "probe replays"
   tests and `test/painted-once.test.ts` pass unchanged. Evidence: the replay
   test and the suite run.
5. **R9 is pinned.** An `available_commands_update`, a `config_option_update`
   and a `session_info_update`, each with a minimal body, leave
   `output.content` empty and push no event and no thinking text. Evidence: the
   test, and the mutation run recorded in the PR.
6. `npm run verify` exits 0. Evidence: the exit code in the PR.
7. `docs/design/v3-engine.md` §5 is titled "Spikes that must land before the
   engine is selectable (R1, R11)", R8 and R9 each say built and name their
   test, and R11 says S1's bridged-call capture is checked against
   `isInternalToolCall()` before the engine is selectable. `CHANGELOG.md`
   `## Unreleased` → `### Changed` has a bullet saying the stream-json reader
   hides kiro's internal tool calls, that no released route draws differently
   because the chat engine is still v2, and naming this spec's tests.

## Verification plan

- **Negative control first.** Write the criterion 1 test and run it against
  the unchanged `src/stream-json-reader.ts`. It fails there, on the "no
  `toolCall` block" assertion, because the `tool_call` case calls
  `surfaceRow()` for every call with an unseen id: the reader cannot see
  `toolId`, so the internal call becomes the `kiro_unknown` row measured above.
  Apply the change and confirm it passes. The criterion 3 test fails on the
  unchanged reader for the same reason (the first `tool_call` already drew the
  row), and passes after.
- **Unit tests, driving the real reader.** A `describe` block in
  `test/stream-json.test.ts` that calls `createStreamJsonReader()` with
  `engine: "v3"` and feeds byte strings built from the two tool calls in §3.3
  and §3.7 and from the three update subtypes §3.3 names. The doc elides the
  call ids and the file path ("b70c...", "tooluse_...", ".../note.txt"), so the
  tests fill them in as `b70c`, `read1` and `note.txt`; it records no body for
  the internal call's `tool_call_update` or for the three subtypes, so those get
  minimal bodies (no v3 capture is committed: §8). It covers criteria 1, 2, 3
  and 5. The trace assertion uses `PI_KIRO_TRACE` and `resetTraceTarget()` as
  the existing "traces the format" test does.
- **Replay test (criterion 4).** For each capture file in
  `probes/stream-json-2.32/`, parse every line and assert `isInternalToolCall()`
  is false for each `tool_call` and `tool_call_update`. The capture list is read
  from the directory, so a capture added later is covered.
- **Mutation check (criterion 5, record in the PR).** Temporarily make the
  reader's `default` branch push the update's JSON to thinking. The criterion 5
  test must fail; restore it and it passes.
- **Live regression (gated `PI_KIRO_LIVE=1`).** Run
  `test/stream-json-live.test.ts`, which needs an authenticated kiro-cli at or
  above the stream-json floor. Its existing cases assert one `kiro_read` row
  for a built-in read and a row for a bridged MCP tool on v2, which is the "no
  v2 row is hidden" invariant on a real process. There is no live v3 case,
  because pi cannot select v3 at this ref; that belongs to the R1 spec.
- **Full suite last.** `npm run verify` on the final tree, exit code recorded
  in the PR (criterion 6).

## Risks

- **A bridged call on v3 is unmeasured.** If v3 sends a bridged MCP call with
  `toolId` and no `toolOrigin`, this predicate would hide it. That is
  unreachable while `CHAT_ENGINE` is `"v2"`, and S1 records exactly that
  payload. Approach step 5 writes the check into R11 in the design doc, so the
  spec that makes the engine selectable inherits it as a precondition rather
  than having to rediscover it.
- **Six v2 tool events is a small sample.** The argument that v2 never sends
  `toolId` rests on those six and on the live test. The trace makes a wrong
  hide visible: a v2 run whose trace holds `chat.stream.internal_tool_hidden`
  is a bug in this predicate.
- **Rollback** is a revert of one commit. Nothing is persisted.
