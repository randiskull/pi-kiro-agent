# Implementation Spec: pi-kiro-agent must interface with both bare pi and GSD without conflict

- Status: Draft (Step 0 verified)
- Area: packaging / host integration
- Target package: pi-kiro-agent (this repo)
- Related: `docs/integrations/gsd-workflow-mcp.md`, `src/index.ts`, `src/readiness.ts`

## Goal

The `kiro` provider (and its `/kiro`, `/kiro-subagents` commands) should be
available whether the binary launching the session is **bare pi**
(`~/.pi/agent/...`) or **GSD**, a pi-derived agent that runs from its own agent
home (`~/.gsd/agent/...`, selected via `GSD_CODING_AGENT_DIR` / `GSD_HOME`).
Loading the extension under either host must not raise errors or interfere with
the other host's extension set.

Concretely, after this change:

1. `kiro/auto` and the `kiro/*` family resolve from a GSD-launched session, not
   only from a bare-pi session.
2. Loading pi-kiro-agent under a GSD agent home produces no load-time error and
   does not perturb GSD's own extensions.
3. The existing bare-pi behaviour is unchanged.

## Observed failure (what triggered this)

A spike run invoked a binary named `pi` that was, in that shell, bound to GSD's
agent home. Two errors surfaced:

```
Error: Failed to load extension "/Users/rndjams/.gsd/agent/extensions/cmux/index.js":
  Extension does not export a valid factory function: .../cmux/index.js
Error: Model "kiro/auto" not found. Use --list-models to see available models.
Hint: Start without extensions using "gsd -ne".
```

- The `gsd -ne` hint and the `~/.gsd/agent/extensions/cmux` path prove the
  process was running under **GSD's agent home**, not pi's.
- The same `pi --list-models` under pi's own home **does** list the full `kiro/*`
  family (`kiro auto`, `kiro claude-opus-5`, `kiro claude-haiku-5.5`, ...), so the
  provider code and the install are healthy - the model was unresolvable only
  because the extension was absent **from that host's extension set**.

## Root cause

This is a **host-scoping / packaging** gap, not a defect in the provider's
`streamSimple`/registration logic.

1. **Separate agent homes, separate extension sets.** GSD resolves its agent dir
   independently (`getAgentDir()` = `$GSD_CODING_AGENT_DIR` if set, else
   `~/.gsd/agent`; confirmed in the installed GSD source, Step 0 below).
   pi-kiro-agent is installed under **pi's** home at
   `~/.pi/agent/npm/node_modules/pi-kiro-agent`, and its provider is registered
   from pi's extension set. GSD's extension set (`~/.gsd/agent/extensions/`)
   contains `claude-code-cli`, `cursor-cli`, `google-cli`, `gsd`, `cmux`, ... and
   **no `kiro` provider**. So a GSD-launched session never registers `kiro/*`.

2. **A stale, unwired copy exists under GSD.** GSD carries a git-synced copy of
   this repo's source at
   `~/.gsd/agent/git/github.com/randiskull/pi-kiro/`, but it is **not wired as an
   extension** under `~/.gsd/agent/extensions/`, so nothing registers it. Its
   presence is a red herring that makes the gap look like it should already work.

3. **The cmux error is independent and benign.** `cmux/package.json` declares it
   a library (`"used by other extensions, not an extension itself"`); `index.js`
   exports named helpers (`initCmuxEventListeners`, ...) with no default factory,
   because the `gsd` extension imports it during its own registration. GSD's
   loader attempted to load it as a standalone extension and complained. It does
   not stop the run and is out of scope for the fix, **except** as a cautionary
   shape: an extension entry point that does not present the host-expected
   factory shape fails exactly this way. pi-kiro-agent must present the correct
   shape under both hosts.

## Scope

### In scope

- Make the `kiro` provider registerable under a GSD agent home via a documented,
  supported mechanism.
- Ensure the extension's entry point loads cleanly under both hosts' loaders
  (correct exported factory shape; no throw at module top level if a host-only
  global is absent).
- A regression test that loads the built extension the way each host loads it and
  asserts the `kiro` provider plus both commands register, with no load-time
  error.
- Documentation: a GSD install/enable path in README and
  `docs/integrations/gsd-workflow-mcp.md`.

### Out of scope

- Fixing GSD's cmux "not a valid factory function" message (GSD-owned; cmux is a
  library mis-picked by GSD's loader).
- Any change to credential handling or billing (unchanged: all traffic stays on
  kiro-cli under the user's entitlement).
- The transport/parsing internals (ACP vs chat) - unaffected by host scoping.

## Step 0 - GSD extension-loading contract (VERIFIED)

Verified against the installed GSD build: `@opengsd/gsd-pi` **v1.22.0**, which
vendors a fork of the pi coding agent as `@gsd/pi-coding-agent`. The loader is
`packages/pi-coding-agent/dist/core/extensions/loader.js`; discovery is
`.../core/extension-discovery.js`; host identity is `.../config.js` +
`dist/app-paths.js`. (Note: the installed build is newer than the v1.2/v1.3
referenced in older steering notes; findings below are from the running code.)

### Q1 - Install root: is there a `pi install npm:<pkg>` path into GSD's home?

**No.** GSD has no npm-install extension-discovery path. `discoverAndLoadExtensions`
loads from exactly three sources, in order:

1. `<cwd>/.gsd/extensions/` - project-local (`CONFIG_DIR_NAME` = `.gsd`).
2. `<agentDir>/extensions/` - global, where `agentDir = getAgentDir()`.
3. Explicitly configured paths (passed in by the CLI/config).

`getAgentDir()` returns `$GSD_CODING_AGENT_DIR` if set, else `~/.gsd/agent`
(derived from `piConfig.name = "gsd"`: `ENV_AGENT_DIR = "GSD_CODING_AGENT_DIR"`,
`CONFIG_DIR_NAME = ".gsd"`). GSD **never scans `npm/node_modules`** for
extensions, so there is nothing resembling `pi install npm:pi-kiro-agent` into
GSD's home. The global extension set is `~/.gsd/agent/extensions/` - the exact
path in the cmux error. This **rules out Option A as originally framed** (there
is no package-install mechanism to lean on).

### Q2 - Discovery: `pi.extensions` manifest field, or `extensions/*/` scan?

**Both, together** - and this is identical to pi. `discoverExtensionsInDir(dir)`
scans one level of an `extensions/` directory. For each entry:

- A bare `*.ts` / `*.js` file directly in `extensions/` loads as an extension.
- A subdirectory is resolved by `resolveExtensionEntries(subdir)`:
  - if `subdir/package.json` has a `pi` **object**, it uses `pi.extensions`
    (array of paths, resolved relative to the subdir, filtered to existing
    files); a `pi` object with missing/empty `pi.extensions` returns `[]` (a
    deliberate **library opt-out** - this is how a shared lib declares "not an
    extension");
  - else it falls back to `subdir/index.ts`, then `subdir/index.js`.
- `.d.ts` files are explicitly skipped (a guard added precisely to avoid the
  spurious "not a valid factory function" error).

So GSD reads the **same `pi.extensions` manifest field pi does**, but only for a
directory that already lives under an `extensions/` root. `mergeExtensionEntryPaths`
additionally lets an installed extension (keyed by its `extension-manifest.json`
`id`) **shadow** a bundled one of the same id.

### Q3 - Required factory shape

**A callable default export** - identical to pi's `ExtensionFactory`. The loader:

```js
const module = await jiti.import(extensionPath, { default: true });
const factory = module;
return typeof factory !== "function" ? undefined : factory;   // else: "...does not export a valid factory function: <path>"
// then: await factory(api)
```

`api` is the GSD `ExtensionAPI`, carrying `registerProvider(name, config)`,
`registerCommand(name, options)`, `on(event, handler)`, `registerFlag(...)`, etc.
- the same surface pi-kiro-agent already uses. jiti means TypeScript entries load
directly, and extensions may `import "@gsd/pi-coding-agent"` (aliased/virtualised
by the loader). cmux fails because its `index.js` has named exports and no
callable default.

**Already satisfied by this repo:** `src/index.ts` exports
`export default async function piKiro(pi: ExtensionAPI): Promise<void>` and
`package.json` declares `"pi": { "extensions": ["./src/index.ts"] }`. The factory
shape and manifest field are already GSD-compatible; the only missing thing is
that nothing places this package **under a GSD `extensions/` directory**.

### Step 0 decision: Option B (with Option C hardening)

Because there is no GSD package-install path (Q1), the provider can only be
registered by making it discoverable under a GSD `extensions/` directory (Q2),
presenting the callable-default factory GSD requires (Q3 - already met). That is
**Option B**. Option A as written (install into GSD's home via a package manager)
is not available and is dropped. Option C (load-safety hardening) still applies.

## Approach

### Option B - Provide a GSD extensions-dir entry (SELECTED)

Ship a thin, documented wiring so the provider registers under a GSD extensions
directory, pointing at the installed/pinned package - never at the stale
`~/.gsd/agent/git/.../pi-kiro/` copy.

Mechanics (pick the lightest that satisfies Step 0):

- Create a subdirectory under a GSD extensions root -
  `~/.gsd/agent/extensions/pi-kiro/` (global) or `<project>/.gsd/extensions/pi-kiro/`
  (project-local) - containing a minimal `package.json` whose
  `pi.extensions` points at the installed package's built entry, or a one-line
  `index.ts` that re-exports the installed package's default factory:
  ```ts
  export { default } from "pi-kiro-agent";
  ```
  This keeps a single source of truth for `registerProvider` (the installed
  package), satisfies the callable-default contract, and relies only on verified
  discovery behaviour.
- Because GSD is externally owned, this wiring is a **documented manual enable
  step**, not something this package writes into `~/.gsd/agent/` unprompted (see
  Risks). If an opt-in installer is desired later, it writes only this wiring
  subdirectory and only on explicit user action.

### Option C - Load-safety hardening (applies regardless)

- The default export is already a callable factory; add a test asserting it
  (direct guard against the cmux-style failure).
- Do not throw at module top level if a pi-only global/singleton is absent under
  GSD; detect host capabilities and degrade (skip a bare-pi-only convenience)
  rather than failing the whole load. Provider registration must not depend on
  any bare-pi-only surface.
- Keep `readiness`-gated registration intact (`src/readiness.ts`) so a cold
  kiro-cli under GSD self-heals exactly as under pi.

### Option A - (DROPPED)

Not available: Step 0 Q1 shows GSD has no npm-package extension-install path.

## Acceptance criteria

1. From a GSD-launched headless session, `--list-models` lists `kiro/auto` and
   the `kiro/*` family, and a one-shot turn against `kiro/auto` completes (the
   spike's failing command, now passing). Evidence: captured command output.
2. Loading the built extension under a simulated GSD agent home raises **no**
   load-time error and registers the `kiro` provider plus `/kiro` and
   `/kiro-subagents`. Evidence: e2e test asserting provider + commands registered
   and no thrown error.
3. The existing bare-pi e2e (`test/extension-load.e2e.test.ts`) still passes
   unchanged - bare pi is not regressed.
4. Under a GSD home, loading pi-kiro-agent does not alter or break GSD's own
   extension set (GSD's bundled extensions still load; the cmux message, if any,
   is GSD-pre-existing and unchanged by this package).
5. README and `docs/integrations/gsd-workflow-mcp.md` document the GSD
   enable path (the Option B wiring subdirectory) and state the host-scoping
   model explicitly (pi home vs GSD home are distinct extension sets, discovered
   from `extensions/` directories, not from `npm/node_modules`).
6. `npm run verify` (typecheck + tests + secret scan) passes.

## Verification plan

- **Negative control first (per repo engineering rule):** before the fix, add the
  GSD-home load test and confirm it **fails** (provider not registered / load
  error). It must fail for the right reason, then pass with the fix.
- **Bare-pi regression:** run `test/extension-load.e2e.test.ts` (npm-pack +
  stubbed kiro-cli, offline) - must stay green.
- **GSD-home load:** new test mirrors the e2e but discovers via a GSD-style
  `extensions/pi-kiro/` wiring subdirectory under a temp agent home (set
  `GSD_CODING_AGENT_DIR`), loads through GSD's documented discovery path, and
  asserts `kiro` provider + both commands + no throw.
- **Live smoke (gated, `PI_KIRO_LIVE=1`):** reproduce the spike - a GSD-context
  `kiro/auto` one-shot turn returns a reply. Skipped in CI like the other live
  tests.
- **Factory-shape assertion:** test that the extension's registered export is a
  callable factory (direct guard against the cmux-style failure).

## Risks and notes

- **GSD is externally owned.** Step 0 confirms there is no supported third-party
  package-install path, so Option B (a wiring entry under a GSD extensions
  directory) is the only route and is documented as a **manual enable step** -
  this package does not write into `~/.gsd/agent/` unprompted.
- **Do not depend on the stale git-synced copy** under `~/.gsd/agent/git/...`;
  the wiring points at the installed/pinned `pi-kiro-agent`.
- **GSD version drift.** Findings are from `@opengsd/gsd-pi` v1.22.0. The
  discovery contract (`extensions/` scan, `pi.extensions`, callable-default
  factory) is stable pi-lineage behaviour, but re-confirm against the installed
  build if a future GSD major changes the loader.
- **ASCII-only** in any host-read string (manifest fields, extension name,
  command ids) per repo convention - no em dashes or smart quotes in
  machine-consumed values.
- The cmux error will likely still appear in GSD runs; that is GSD's to fix.
  Note it in the docs so operators do not misattribute it to pi-kiro-agent.
